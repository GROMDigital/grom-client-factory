The Grom Diagnosis Engine

It reads one client account and works out what is losing them money, then tells you what to fix and in what order. It never changes anything.

Skill grom-client-factory:grom-diagnosis-engine · plugin 1.6.0 · describes what the code actually does, as of the SK Skin and Grom UK runs of 27 July 2026

What it is, in one paragraph

Point it at a sub-account. It reads that account twice over: once through the public side for what happened to real people, and once through the internal side for how the automation is actually built and what every message says. Then a series of expert agents read that evidence and argue about it. What comes out is a ranked list of problems, one file per problem saying what to change, the replacement copy written out message by message, and a running order for doing the work.

It is read-only end to end. Nothing it produces is applied automatically, because everything it touches sends real messages to real patients.

The two rules that shape everything else

1. The auditor decides what to analyse. It is never told.

Nothing anywhere says what a workflow is for. No config file names them, and deliberately never will. Stage 1 works it out from the evidence. That is what lets it run against any account whether or not it was built to our standard, and it is what catches a workflow whose real job is not the job its name claims. On Grom UK it found four of those.

2. No hardcoded checklists.

There is no list of best practices being ticked off. Expert agents read the evidence and form an opinion, held to a contract that forces them to state their confidence and a test that would prove them wrong. This was a deliberate correction: a rule checker only finds the things you already thought of, which is the opposite of the point.

The five stages

Each stage is agents reading and thinking. Between every pair sits a plain program that validates the work and prepares the next one. The number of agents comes from the account: fewer workflows, fewer experts.

1
One expert derives the map

Reads the whole account cold and works out what it is: what journey it runs, what each workflow appears to be for, which sit on the money path, which are delivery, which look abandoned. Where a name and the behaviour disagree, it says so and goes with the behaviour.

1 agent · every workflow must be accounted for or the map is refused

2
One expert per workflow, and per AI agent

Each sees its object whole: the configuration, what actually happened to real contacts, every message in full, what runs alongside it, and the metric it is meant to move. This is the heart of it. It answers "is this good, where does it lose people, and what should each message say instead".

SK Skin: 20 agents, being 16 workflows and 4 AI agents · Grom UK: 19

3
Three experts read the whole account

One follows the lead journey and the numbers to find where people drop out. One reads the account as a single system: collisions, duplicate automation, what one lead experiences moving across sequences. One reads every message as a single stream, in the order a real person receives them.

3 agents · each reads over 100,000 words and is not allowed to skim

4
Group, rank, and write it up

A plain program, not an agent. It validates every finding, refuses malformed ones by name, groups the rest into root causes, ranks them, and writes one solution package per cause.

no agent · deterministic

5
One expert sets the running order

Reads the ranked problems and decides what is really one job, what has to land first, and which fixes pull against each other. It is forbidden from re-diagnosing: the contract gives it nowhere to put a new finding.

1 agent · every problem must be placed exactly once

Why one expert per workflow, rather than one per topic

This is the most important design decision, and it came from getting it wrong first. Originally a workflow was split across three specialists: one looked at configuration, one at copy, one at the numbers. None saw it whole, so none could produce the sentence that actually mattered:

This sequence sends ten messages, keeps sending after the lead has already replied, and the text at the moment of peak interest withholds the rebooking link.

That is configuration, runtime and copy in one thought. No specialist reading a third of the object could write it. The first version of this only "surfaced the obvious things" for exactly that reason, and the fix was structural rather than better prompting.

What it reads

SideWhat it gets
PublicContacts, conversations, appointments and opportunities. What actually happened to real people.
InternalEvery workflow's real configuration and step graph, the AI agent setups, and the actual body of every email, including ones held in the template library.

The internal side needs a login token that expires every hour and can only be captured from a real browser session. That is what uxie-ghl-factory:connect is for. Check it before starting a run rather than during, because an expired token jams the connection for every call that follows.

Running one, start to finish

First time on a new account

node scripts/init-account.mjs \
  --project ~/.grom-audit-runs/<label> --location <locationId> --label <label> \
  --credential-env <ENV_VAR> --token-file <path to the token>

One command. It reads the account's own company id, timezone and name from the account itself rather than trusting anyone to type them. That matters more than it sounds: SK Skin is a Melbourne clinic whose account timezone is Sydney, and using the city would have shifted every weekly boundary with nothing complaining.

Do this before the first run

It also writes an empty facts file for the account. Fill it in before running anything. Ask the client what would make a number mean something other than what it looks like: who marks appointment outcomes, which calendars are deliberately two-phase, what is switched off on purpose, whether deposits are taken, where test data lives.

The evidence is sealed the moment a run starts, so a fact added afterwards can never reach an expert. On SK Skin this is what stopped the report announcing a catastrophic no-show rate that was really a recording gap.

Every run after that

audit run          collects both sides, measures, writes the stage-1 prompt
  → 1 agent        the account map
audit map          validates it, writes one prompt per workflow and per agent
  → N agents       one per object
audit reviews      collects them, writes the three account-wide prompts
  → 3 agents       journey, system, message stream
audit investigate  groups, ranks, writes the packages and the backlog
  → 1 agent        the running order
audit plan         validates it, writes PLAN.md and REPORT.html

If you lose your place, audit briefs tells you which stage a run is at, worked out from what is on disk rather than from a status somebody wrote down.

Roughly an hour and a half for a 16-workflow account, and around three million agent tokens. That cost scales with the number of workflows and is the dominant cost of the whole thing.

What you get, and the order to read it

Everything lands in the client's own folder under Grom Diagnosis Engine (Weekly Audit)/<account>/<date>/, in the same shape for every account and every week, so an agent can be pointed at the folder and rely on it.

FileWhat it is
START-HERE.mdThe read order, the account's caveats, and what the run could not see. Written for whoever or whatever opens the folder.
PLAN.mdStart here. The running order: what to do first, what blocks what, what conflicts.
BACKLOG.mdThe ranked problems in one table, with confidence and how many experts found each.
packages/One file per problem: what is wrong, what to change, how you will know it worked. The action list.
reviews/One per workflow and per AI agent. The replacement copy lives here, message by message.
CHANGES-MADE.mdA template. Fill it in as you do the work. See below.
LAST-WEEK.mdFrom the second run on: what you said you changed against what the account still shows.
INVESTIGATION.mdThe full argument behind every problem, for when you disagree with one.
REPORT.htmlThe same material as a page, for a person to read.
evidence/The sealed briefs and every prompt an expert read, so any claim can be traced.

The one thing that is not obvious: when a package says "rewrite this message", the actual words are in reviews/, not in the package. The packages say what and why. The reviews carry the text.

Week over week

Every run records what it found, per account, and compares itself against every run before it. This is automatic and there is nothing to pass in. You get three answers per problem: new, recurring with how long it has been there, and absent.

Identity is not the labels the experts use, because they invent fresh ones every week. A problem is recognised by what it is: the mechanism, plus the specific workflows and metrics it touches. That match is strict on purpose. Rename a workflow and it reports a new problem rather than quietly claiming the old one came back, because a wrong match across weeks is worse than an unmatched pair.

The thing to understand

Absent does not mean fixed, and the engine will never say it does. A problem can vanish because it was solved, because an expert framed it differently this week, because the evidence moved, or because its finding was refused on a technicality. Nothing in the account can tell those apart.

That is what CHANGES-MADE.md is for. The engine writes it as a template, already listing this run's problems in the plan's order, and whoever does the work fills in what they actually did. The next run reads it and separates the three cases that matter:

  • Changed, and now gone. Treat as fixed. The only combination that earns the word.
  • Changed, and still here. The fix did not work, or did not address the cause.
  • Gone, and nobody touched it. Unexplained. A reason to look, not to celebrate.

If nobody fills it in, nothing breaks. The page just says plainly that nothing can be concluded.

What it cannot do

These are real limits, not modesty. They are stated in the outputs too.

LimitWhat it means for you
A finding is an argument, not a verdictNothing re-checks a claim after stage 3, so a wrong finding travels intact into the plan. Every package carries a test that would settle it. Run the test before expensive work.
Runtime is opt-inUnless it is requested for a specific workflow, claims about how a workflow behaves are read from how it is built.
It cannot prove causationNothing proves the configuration read today was in force during the weeks being measured. A setup can be called consistent with an outcome, never the cause of a past one.
Small accounts, soft percentagesSK Skin had 21 appointments. Two or three records move a percentage a long way. Read ratios as direction.
The ranking order is imperfectOn SK Skin the most serious and most corroborated problem ranked fourth. Read the top handful as a set rather than a strict order.

The most convincing evidence that it works is convergence. On Grom UK, five experts who could not see each other's work traced back to one defect nobody had named: six workflows fire the same bare event, and both a signed-client rail and a cold-lead rail listen to it unfiltered, so cold leads were told "since you signed up" and signed clients were told their clinic was broken.

On SK Skin, three independent reviewers reached the same hole from different directions. The ads pixel workflow reported leads reaching no nurture. The long-term nurture workflow turned out to be an empty draft with no trigger and no steps. And the chat agent only re-engages someone who explicitly says no, so the roughly 200 of 213 conversations that simply go quiet meet nothing at all.

Read-only. Every fix is a proposal for a human to approve. Nothing in this engine writes to a client account, and the packages say so on every page.
